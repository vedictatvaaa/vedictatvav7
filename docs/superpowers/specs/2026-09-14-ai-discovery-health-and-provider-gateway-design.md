# AI Discovery Health Repair and Central Provider Gateway

**Date:** 2026-09-14  
**Status:** Approved design pending written-spec review

## Goal

Make Pandit discovery health and location rectification reliable from Admin, while providing one server-side ChatGPT-compatible provider gateway for Coolify and self-hosted Vedic Tatva deployments.

The system must repair safe deterministic problems automatically, keep AI-generated changes review-only by default, and never publish unsupported facts.

## Scope

This work covers:

- Discovery Health diagnostics and error reporting
- Admin one-click safe repair
- Admin choice-based AI suggestions and application
- Location rectification reliability
- Storefront/indexability validation after repair
- Central AI provider configuration and routing
- Coolify/self-hosting environment documentation and diagnostics

This work does not replace the existing public-governance rules, location authority, exact-coordinate policy, storefront publication gates, or SEO route rules.

## Safety policy

### Deterministic changes may auto-apply

The repair engine may apply a change automatically only when the value is an exact authoritative match or a derived value with no factual interpretation:

- Canonical state/city alias normalization
- Exact active state/city ID match
- Canonical slug normalization when the target is unambiguous
- Rebuilding derived indexability metadata from authoritative fields
- Rebuilding stale public projections without changing source facts
- Recomputing sitemap/SEO notification state after publication gates pass

Exact Pandit coordinates are never replaced with city centroids or regenerated by this workflow.

### AI changes require Admin review

AI may draft a change only from an allow-listed verified source snapshot. A draft remains non-public until an Admin applies it. The default Admin action is:

- `Apply safe fixes`
- `Create AI suggestions for review`

The Admin may then apply or reject each suggestion, or select a reviewed group. There is no default “apply all AI output” action.

AI must not create or infer:

- People, identity, registration numbers, qualifications, languages, or experience
- Locations, coordinates, service areas, travel coverage, or availability
- Services, pricing, packages, booking history, ratings, reviews, or testimonials
- Health, legal, financial, outcome, guarantee, or supernatural claims
- Contact information, credentials, passwords, private notes, or internal governance fields

## Central AI provider gateway

Create a server-only `ai-provider` module with one typed interface for text generation and structured JSON generation. Feature modules request a task name, model preference, bounded input, output schema, and token budget; they do not instantiate `OpenAI` directly.

### Configuration

The gateway uses environment variables so the same code runs on Replit, Coolify, and self-hosted installations:

- `AI_PROVIDER=openai-compatible`
- `OPENAI_API_KEY` — required for enabled production AI calls
- `OPENAI_BASE_URL` — optional; defaults to `https://api.openai.com/v1`
- `OPENAI_MODEL` — default deployment model
- `OPENAI_ORG` — optional organization header where supported
- `AI_ENABLED=true|false` — explicit operational switch, default `true` only when a key is configured
- `AI_REQUEST_TIMEOUT_MS` — bounded request timeout
- `AI_MAX_RETRIES` — bounded retry count

The provider remains OpenAI-compatible even when `OPENAI_BASE_URL` points to an organization-owned gateway or compatible self-hosted endpoint. The API key is read only by the server process and never returned to the browser, stored in database rows, written to logs, or included in Admin diagnostics.

If the gateway is disabled or missing configuration:

- Deterministic health checks and safe repairs continue to work
- AI suggestions return a clear `ai_provider_unavailable` state
- No silent fallback invents content
- Existing feature-specific fallback behavior remains only where it is already an explicit product contract

### Provider request contract

Every request includes:

- Feature/task identifier
- Model and timeout policy
- System safety instructions
- Allow-listed verified source snapshot
- Strict structured-output schema
- Correlation ID that contains no secrets or personal contact values

Every response is validated for schema, unsupported factual entities, private data, and source provenance before it becomes a draft. Provider errors are normalized into safe Admin-facing categories and detailed server logs contain status/category, not prompts or contact data.

### Migration of existing AI modules

Move existing direct `OpenAI` construction behind the gateway in bounded batches:

- Pandit storefront content drafts
- Location interpretation
- Blog/content generation
- Jyotish/rashifal generation
- Any remaining server-side AI feature found by the provider audit

The gateway preserves existing prompt/output contracts during migration. A feature is not considered migrated until its direct client construction is removed or explicitly documented as an external non-LLM integration.

## Discovery Health engine

### Diagnostic model

Create a typed diagnostic result with:

- Pandit ID and safe display identity
- Category and stable error code
- Severity: `safe_fix`, `review`, `blocked`, or `system_error`
- Current source values and safe public labels only
- Deterministic proposed change, if any
- AI suggestion metadata, if any
- Required next action
- Whether the record is eligible for publication/indexing

Diagnostics must never include phone, WhatsApp, email, password, session, private Admin notes, or raw provider prompts.

### Diagnostic categories

The health engine checks:

1. Canonical state/city IDs and active location records
2. Alias and location-review status
3. Exact-coordinate presence/provenance without replacing coordinates
4. Public governance: verified, active, not banned/suspended/archived/on leave
5. Directory/search eligibility
6. Storefront existence, status, and publication
7. Biography, image, languages, and public profile completeness
8. Active canonical service assignment
9. Bookable mode and service eligibility
10. Canonical `/pandit/:slug` route and redirect integrity
11. Canonical metadata, JSON-LD, sitemap eligibility, and `noindex` state
12. Public storefront response and API projection consistency
13. Source snapshot freshness for reviewed AI content

Each failure has one stable code and a human-readable explanation. Multiple failures may be shown together without exposing hidden governance details to public users.

## Admin workflow

### Scan

`Run discovery health scan` runs read-only diagnostics across all Pandits or a selected scope. It stores a batch ID and returns counts by safe fix, review, blocked, and system error.

### Safe repair

`Apply safe fixes` rechecks each candidate inside a transaction, applies only deterministic changes whose source values still match the scan snapshot, and records before/after values in an Admin audit record. Stale candidates are skipped and marked for rescan.

### AI suggestions

`Generate AI suggestions` sends only eligible allow-listed snapshots to the central provider. Suggestions are saved as review records with:

- Original source snapshot hash
- Proposed text or structured change
- Prompt/provider/model metadata without secrets
- Validation result
- Reviewer and review timestamp

Suggestions cannot change public status, governance flags, location IDs, coordinates, services, prices, or booking fields.

### Apply or reject

An Admin can review each suggestion and choose `Apply` or `Reject`. Applying rechecks the current source snapshot hash and all relevant public gates. If the source changed, the suggestion is stale and must be regenerated.

### Publish and index

After changes are applied, `Validate & publish eligible storefronts`:

- Requires verified, active, governed Pandit
- Requires active canonical location records
- Requires published storefront
- Requires approved public content
- Requires active canonical service and valid bookable mode
- Requires current source snapshot hash
- Requires canonical route integrity
- Requires no `noindex` or blocking governance state

Only then may the workflow update derived SEO projections, sitemap eligibility, and indexing notifications. Unresolved or review-required records remain withheld.

## Location rectification reliability

The rectification flow must have separate, explicit operations:

- `Preview exact matches`
- `Apply exact matches`
- `Generate AI location suggestions`
- `Edit proposal`
- `Approve proposal`
- `Reject proposal`
- `Apply approved proposal`

The API must return structured validation errors instead of generic 400 responses. It must be idempotent by Pandit, source snapshot, and proposal kind. Concurrent applies must lock the Pandit row and recheck the current source before writing.

AI location interpretation may rank existing candidate state/city IDs but may not create a new location, modify coordinates, or approve an ambiguous candidate. Confidence below the configured review threshold remains review-only.

## Error handling and observability

- System errors are distinct from Pandit data errors.
- Provider timeout, invalid JSON, rate limit, and unavailable configuration are retryable/operational states.
- Database errors roll back the current repair unit.
- Batch operations continue across independent records and return per-record outcomes.
- Every batch has a correlation ID and Admin audit entry.
- Logs include batch ID, Pandit ID, stable error code, provider task, and duration; never prompt bodies, API keys, phone numbers, or WhatsApp numbers.
- Retrying a batch does not duplicate applied changes or published SEO notifications.

## Self-hosting and Coolify

Document the provider environment variables in the deployment configuration and Admin diagnostics. The diagnostics page shows:

- Provider mode
- Base URL hostname only
- Model name
- Enabled/disabled state
- Last successful provider health check
- Last failure category

It never shows API keys or full URLs containing credentials. Coolify deployment must fail clearly when production AI is configured as enabled without a key, while allowing deterministic-only operation when AI is intentionally disabled.

## Testing

### Health and rectification

- Exact alias/state/city repair applies and preserves coordinates
- Ambiguous location remains review-only
- Stale source snapshot cannot be applied
- Concurrent apply cannot overwrite newer Admin edits
- Safe repair is idempotent
- Hidden, banned, suspended, archived, on-leave, unresolved, and noindex Pandits remain unpublished
- Storefront, route, metadata, and sitemap gates agree
- Every error code includes an actionable reason

### AI gateway

- OpenAI-compatible base URL is honored
- Default official endpoint is used when no base URL is configured
- Missing key disables AI without breaking deterministic health
- Timeout, rate limit, invalid JSON, and unsupported entity responses are safe
- API key and private/contact fields never reach browser responses, logs, audit records, or provider payloads
- All migrated modules use the gateway

### Workflow and UI

- Scan, safe repair, AI suggestion, apply, reject, publish, and retry states
- Batch partial success reporting
- Admin confirmation before mutating actions
- Mobile and desktop health list behavior
- Production build and startup with AI enabled and disabled

## Rollout

1. Add the gateway in disabled-compatible mode.
2. Add health diagnostics and read-only scan.
3. Repair deterministic location and projection errors.
4. Add AI suggestion generation and review controls.
5. Migrate existing AI modules to the gateway.
6. Enable publish/index actions only after the full gate suite passes.
7. Run a development and staging audit before Coolify rollout.

## Out of scope

- Automatic creation of factual Pandit data
- Automatic approval of ambiguous locations
- Replacing exact coordinates
- Public AI-generated claims without Admin review
- Provider-specific browser calls
- Storing API keys in the database or source repository
